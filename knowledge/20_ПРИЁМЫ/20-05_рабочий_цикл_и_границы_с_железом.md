# Рабочий цикл и границы с железом

## Что можно без спроса, а что нет

* **Без спроса** — только чтение: `probe()`, `info()`, `read32()`,
  `watch()`, `sample()` (у ST-Link те же функции в `mcukit.stlink`, кроме
  `sample()` — его там нет). `save()` — тоже чтение: у J-Link со стопом
  ядра на время чтения; у ST-Link ядро не останавливается и не
  сбрасывается, пока не потерян `mode=HOTPLUG` (умолчание, 30-08).
  Передавая `mode=` вручную, не терять `HOTPLUG` там, где операция должна
  быть безобидной.
* **Только с согласия человека**: `flash()` и всё, что пишет во флеш или
  в байты настройки; снятие защиты (стирает весь флеш); `reset_run()` —
  прерывает работающий код. Перед первой записью в плату с неизвестной
  прошивкой — `save()` старого содержимого.
* **Никогда** не проверять связь J-Link профилем чипа
  (`device="GD32F470VK"`) — только `Cortex-M4`: скрипт производителя без
  связи сам запускает стирание (30-02). Для ST-Link этого ограничения нет
  (docstring `mcukit.stlink`), но запись всё равно — только с согласия.
* Питание и проводку делает человек. Ядро не отвечает — сначала спросить
  про **общую землю** и **питание платы**, а не гадать по уровням линий
  (30-01, 30-03).

## GD32 — J-Link

```python
p = mk.probe()                               # 1. зонд и VTref
i = mk.info(reads=["mem16 0x1FFF7A22 1",     # 2. ядро, профиль Cortex-M4
                   "mem32 0x40023C14 1",     #    защита (GD32F4/STM32F4)
                   "mem32 0x08000000 4"])    #    пуст ли флеш
mk.save(r"D:\проект\old.bin", 0x08000000, 0x10000)   # 3. если не пуст

r = mk.build(r"D:\проект\прошивка").check()  # 4. сборка копией
mk.flash(r.bin, device="GD32F470VK", min_vtref=3.1)  # 5. запись + сверка
mk.watch(mk.symbol(r.elf, "blink_count"))    # 6. растёт — код идёт
```

`flash()` сам повторяет шаги 1–2 и без ответа ядра профиль чипа не
запускает. `min_vtref` — выше порога супервизора питания платы. Порядок
и почему — 20-01.

## STM32 — ST-Link

```python
i = mk.stlink.info()                                  # 1. ядро, ID, В
mk.stlink.save(r"D:\проект\old.bin", 0x08000000, 0x20000)  # 2. весь флеш, всегда

r = mk.build(r"D:\проект\прошивка").check()           # 3. сборка копией
mk.stlink.flash(r.bin, addr=0x08000000, min_voltage=3.0)   # 4. запись + сверка + сброс
mk.stlink.watch(mk.symbol(r.elf, "loop_count"))        # 5. растёт — код идёт
```

Код возврата обманывает в обоих модулях: у J-Link сценарий обрывается
молча с кодом 0 (30-05), у ST-Link код 1 даже при удачном подключении с
`sn=` (30-07); `Result.ok` это учитывает. Растущий счётчик у ST-Link
проверяет ещё и сам способ чтения: статичное чтение не ловит сброс ядра
обычным `connect` (30-08).

## Новый проект из шаблона

* **GD32/STM32F4 (J-Link), со светодиодами** — `templates/blink_f4/`:
  поправить `src/config.h` (светодиоды), `link.ld` (размер флеша),
  `project.py` (имя чипа, порог VTref).
* **STM32L0/Cortex-M0+ (ST-Link), без периферии** — `templates/counter_l0/`:
  только счётчик в ОЗУ, GPIO не трогает — для первой проверки записи на
  неизвестной или чужой плате (GPIO вслепую может задеть управление
  реальной нагрузкой). Поправить `link.ld` под реальный размер флеша,
  `project.py` (адрес, напряжение, `BACKUP` — обязателен).

Шаблон копируется в папку проекта; при копировании вписать в
`project.py` `KIT = r"<корень набора>"` — папку, из которой прочитан
`SKILL.md`. Затем `python run.py` (только сборка — `--build`). Как
`run.py` ищет набор — 40-01.

## Состав библиотеки

| Модуль | Что в нём |
|---|---|
| `env` | J-Link, ST-Link/STM32CubeProgrammer, GCC, make — поиск; рабочие папки; `utf8_console` |
| `jlink` | `run`, `Result`, `probe`, `info`, `read32`, `watch`, `sample`, `save`, `reset_run`, `flash` — плоские имена `mk.*` |
| `stlink` | `run`, `Result`, `probe`, `info`, `read32`, `watch`, `save`, `reset_run`, `flash` — только `mk.stlink.*`, без `sample` |
| `build` | `build`, `BuildResult`, `size`, `symbol`, `vectors` |

Сигнатуры — docstring в `mcukit/*.py`.
